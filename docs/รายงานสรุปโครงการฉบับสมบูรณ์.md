# รายงานสรุปโครงการ LCB Office CRM + ERP

**ระบบ:** Laem Chabang Inter Auto Tire  
**โดเมนเป้าหมาย:** `https://app.laemchabanginterautotire.com`  
**วัตถุประสงค์:** สรุปสถานะการพัฒนา สิ่งที่ทำแล้ว สิ่งที่เหลือ ความเสี่ยง และแผนเตรียมใช้งานจริง  
**ขอบเขต:** ตรวจจาก source code และเอกสารใน repository ณ branch ปัจจุบัน ไม่ได้ตรวจภายในระบบ PHP เดิม ฐานข้อมูลจริง DNS/hosting หรือบัญชี LINE/Facebook จริง

> **ข้อสรุปผู้บริหาร: ยังไม่พร้อมเปิดใช้งานจริง (NO-GO)** ปัจจุบันเป็นต้นแบบ Next.js ที่มีหลายหน้าจอ แต่ CRM ยังใช้ข้อมูลเดโมในไฟล์ JSON ไม่ได้ใช้ฐาน MySQL เดิม, ระบบล็อกอินจริงยังไม่เชื่อม, การสะสมแต้มด้วย QR ยังไม่ได้ทำ และ Rich Menu แบบ 6 ช่อง 3×2 ยังไม่ได้ทำ การตั้ง `DATABASE_URL` หรือ token เพียงอย่างเดียวไม่ทำให้ระบบทั้งหมดพร้อม production

## 1. เป้าหมายและหลักการของโครงการ

1. พัฒนาระบบ Next.js เพื่อดูแลลูกค้า สินค้า โปรโมชัน การนัดหมาย บริการ แชท และช่องทางเผยแพร่จากศูนย์กลาง
2. ใช้ฐานข้อมูล MySQL เดิมของระบบ PHP **โดยไม่เปลี่ยน schema ชื่อตารางหรือคอลัมน์ และไม่ย้ายข้อมูลโดยไม่ได้รับอนุมัติ** ต้องสำรวจโครงสร้างจริงก่อนเชื่อม
3. เปิดแอปใหม่บน `app.laemchabanginterautotire.com` โดยคง `office.laemchabanginterautotire.com` สำหรับระบบเดิมระหว่างเปลี่ยนผ่าน
4. ออกแบบ LINE Rich Menu แบบ 6 ช่องที่ปรับแต่งได้ และระบบสมาชิกสะสมแต้มผ่าน QR ตามรายละเอียดที่ร้านอนุมัติ
5. แยก staging และ production รวมถึงป้องกันข้อมูลส่วนบุคคลและการส่งข้อความหรือแก้ข้อมูลจริงโดยไม่ตั้งใจ

## 3. โครงสร้างระบบเป้าหมาย

```text
ลูกค้า: LINE OA / เว็บมือถือ
  ├─ Rich Menu → โปรโมชั่น | สินค้า | จอง | สมาชิก | Google Maps | ติดต่อ
  ├─ ข้อความ → LINE webhook → inbox → พนักงาน / ระบบช่วยตอบ
  └─ หน้าสมาชิก → ยอดแต้ม / ประวัติ / QR (ต้องพัฒนา)

พนักงาน: แอป Next.js บน app.laemchabanginterautotire.com
  ├─ Cockpit, ลูกค้า, สินค้า, โปร, จอง, ศูนย์บริการ
  ├─ สมาชิก/สแกน QR/แต้ม (ต้องพัฒนา)
  ├─ LINE Rich Menu, publishing, รายงาน
  └─ บัญชีผู้ใช้, สิทธิ์, audit และการอนุมัติ

ชั้นบริการฝั่งเซิร์ฟเวอร์ → MySQL เดิมตาม schema ที่ตรวจแล้ว
                         → LINE / Facebook APIs ตามสิทธิ์และการตั้งค่าจริง
```

โครงสร้างนี้เป็น **เป้าหมาย** ไม่ใช่การยืนยันว่าทุกส่วนเชื่อมกันแล้ว หน้าพนักงานภายในและหน้าสาธารณะสำหรับลูกค้าต้องแยกการเข้าถึง โดยเก็บ token และ credentials ไว้บนเซิร์ฟเวอร์เท่านั้น

## 4. รายละเอียด LINE Rich Menu 6 ช่อง

**รูปแบบเสนอ:** 3 คอลัมน์ × 2 แถว ปรับลำดับ ชื่อ ภาพ และปลายทางได้ ก่อนเผยแพร่ต้องมี preview และการอนุมัติ

| ตำแหน่งเสนอ | ช่อง | พฤติกรรม | ข้อมูลที่ต้องยืนยัน |
|---|---|---|---|
| บนซ้าย | โปรโมชั่น | เปิดหน้ารวมโปรที่ใช้งาน | หน้าลูกค้า เงื่อนไข/ระยะเวลาโปร |
| บนกลาง | สินค้า | เปิดแค็ตตาล็อกสินค้า/บริการ | หมวดสินค้าและการแสดงราคา/สต็อก |
| บนขวา | จองนัดหมาย | เปิดฟอร์มจองสำหรับลูกค้า | เวลาให้บริการ ข้อมูลที่ต้องกรอกและวิธียืนยันนัด |
| ล่างซ้าย | สมาชิก | เปิดหน้าสมาชิก ยอดแต้ม ประวัติ และ QR | วิธีสมัคร/ยืนยันตัวตนและกติกาแต้ม |
| ล่างกลาง | Location | เปิด **Google Maps โดยตรง** | **รอลิงก์ Maps จริงของร้าน/สาขา** |
| ล่างขวา | ติดต่ออื่น ๆ | เปิดหน้ารวมช่องทางติดต่อ หรือส่งข้อความ | เบอร์โทร LINE/Facebook เวลาเปิด–ปิด และรูปแบบที่ต้องการ |

**สิ่งที่ต้องพัฒนาเพิ่ม:** template 3×2 และพิกัดคลิกตรงภาพ, ตั้งชื่อ/URL/ข้อความ, อัปโหลดภาพและ preview, ร่าง/อนุมัติ/เผยแพร่, บันทึกเวอร์ชันและขั้นตอน rollback, ตรวจสิทธิ์ และทดสอบบนมือถือ/LINE test account หน้าพนักงาน `/promotions`, `/products` และ `/service` ต้องล็อกอิน จึงไม่ควรใช้แทนหน้าลูกค้าสาธารณะโดยตรง

**ข้อจำกัดปัจจุบัน:** ระบบสร้างเมนูได้สูงสุด 6 ปุ่มแบบแถบแนวตั้งเท่ากันเท่านั้น การสร้าง 3×2 และระบบปรับแต่งตามตารางยังเป็นงานค้าง; ชื่อปุ่ม metadata ไม่ได้สร้างภาพให้โดยอัตโนมัติ

## 5. สมาชิกสะสมแต้มด้วย QR

### สถานะ

**ยังไม่ได้พัฒนา** ไม่พบระบบ QR สมาชิก/สแกน/ledger/แลกแต้มในโค้ดที่ตรวจ ระดับลูกค้า (tier) เดโมไม่ใช่ระบบสะสมแต้ม

### ขั้นตอนใช้งานที่เสนอ

1. ลูกค้าสมัครหรือยืนยันตัวตนและเชื่อม LINE กับข้อมูลลูกค้าโดยได้รับความยินยอม
2. เปิดช่องสมาชิกใน Rich Menu เพื่อดูยอด ประวัติและ QR หลังผ่านการยืนยันตัวตน
3. พนักงานที่มีสิทธิ์สแกน QR เลือกบิลหรือใบงานที่ชำระและมีสิทธิ์ จากนั้นตรวจสอบยอดและยืนยันการให้แต้ม
4. ระบบบันทึกรายการแต้มพร้อมเลขอ้างอิง ผู้ทำรายการ เวลา และกติกาที่ใช้ แล้วแสดงยอด/ประวัติให้ลูกค้า
5. การแลกแต้มและการคืน/ยกเลิกต้องมีขั้นตอนอนุมัติและประวัติปรับย้อนกลับ ไม่ลบประวัติเดิม

### เงื่อนไขความปลอดภัยและข้อมูล

- QR ควรใช้ token สุ่มอายุสั้น ไม่แสดงข้อมูลส่วนบุคคล และป้องกันการใช้ซ้ำ; การสแกนเพียงอย่างเดียวต้องไม่เพิ่มแต้ม
- ตรวจสิทธิ์พนักงาน แยกสิทธิ์ดู/เพิ่ม/แลก/ปรับ/อนุมัติ; มี audit และเหตุผลของการปรับ
- ป้องกันบิลซ้ำและการกดพร้อมกันด้วย idempotency และ transaction; รองรับเครือข่ายขาดและกล้องใช้ไม่ได้
- **ต้องตรวจ schema MySQL เดิมก่อน** หากไม่มีที่เก็บ ledger/QR/audit ให้เสนอทางเลือกที่ไม่แก้ schema เดิม หรือขออนุมัติแยกก่อน ห้ามเพิ่มตารางหรือเปลี่ยน schema เดิมเอง
- กำหนดนโยบายความเป็นส่วนตัว ความยินยอม อายุการเก็บ และการสำรอง/กู้คืนข้อมูล

### กติกาที่ต้องให้ร้านตัดสินใจ

อัตราเงินบาทต่อแต้มและการปัดเศษ; การคำนวณก่อน/หลังส่วนลดและ VAT; สินค้า/บริการที่เข้าร่วม; วันให้แต้ม; อายุแต้ม; ของรางวัลและเงื่อนไขแลก; การคืนสินค้า/ยกเลิกบิล; การรวมสมาชิกซ้ำ; บทบาทผู้มีสิทธิ์ปรับและอนุมัติ **ยังไม่มีการกำหนดตัวเลขหรือกติกาเหล่านี้**

## 6. ความเสี่ยงและสิ่งที่ต้องแก้ก่อนใช้งานจริง

| ระดับ | ความเสี่ยง | การดำเนินการที่ต้องทำ |
|---|---|---|
| วิกฤต | JSON เป็นข้อมูลเดโม เก็บใน process/ไฟล์ และการเขียนล้มเหลวอาจไม่แจ้ง; ไม่เหมาะกับหลาย process/serverless | เชื่อม MySQL เดิมด้วย transaction ทดสอบ backup/restore และความถูกต้องก่อนใช้ข้อมูลจริง |
| วิกฤต | ระบบ login จริงยังไม่เชื่อม; production ปิดบัญชีเดโม จึงยังเข้าใช้งานจริงไม่ได้ | เชื่อมบัญชีเดิมตาม schema และ hash จริง พร้อมตรวจ role ทุก server action/API และ rate limiting |
| สูง | การส่งภายนอกอาจจำลองสำเร็จเมื่อไม่มี token; publishing action ปัจจุบันตั้งสถานะโพสต์หลังเรียกแต่ละช่องทางโดยไม่แยกความสำเร็จจริงให้ครบ | แยก demo/prod, บันทึกผลต่อช่องทาง, retry/idempotency และการอนุมัติก่อนส่ง |
| สูง | webhook ต้องจัดการการส่งซ้ำ การตอบไม่สำเร็จ และความถูกต้องของสถานะ | ทดสอบ signature/secret, deduplicate events และบันทึก/ติดตามข้อผิดพลาดอย่างปลอดภัย |
| สูง | ไม่มีการยืนยันความสามารถ schema/ระบบเดิมและการทำงานของ LINE/Facebook จริง | สำรวจแบบ read-only และทดสอบ staging กับ test accounts ก่อนเปลี่ยนระบบจริง |
| สูง | ข้อมูลลูกค้า/QR/แต้มอาจเปิดเผยหรือถูกใช้ผิดสิทธิ์ | ออกแบบสิทธิ์, การยืนยันตัวตน, privacy, audit และทบทวนความปลอดภัยก่อนเปิด |
| ปานกลาง | metrics ปัจจุบันสุ่มและไม่มี scheduler ที่ติดตั้ง | แสดงว่าเป็นเดโมจนเชื่อม insights จริงและกำหนด scheduler |
| ปานกลาง | การย้ายโดเมน/เปลี่ยน webhook อาจกระทบระบบเดิม | คง `office.` จนผ่าน UAT; เตรียม DNS/webhook rollback และสำรองข้อมูล |

| 1. สำรวจ | รับ schema ที่ลบข้อมูลส่วนบุคคล, สำรวจบัญชี/สิทธิ์ และกระบวนการ PHP เดิม | เอกสาร mapping และรายการข้อจำกัดโดยไม่เปลี่ยนฐาน | เจ้าของระบบ + ผู้ดูแลฐานข้อมูล + นักพัฒนา |
| 2. ฐานและความปลอดภัย | เชื่อม MySQL เดิมและ auth จริง ตรวจสิทธิ์ทุก action/API และ transaction | ทดสอบกับสำเนาฐาน staging; backup/restore และสิทธิ์ผ่าน | ผู้ดูแลฐานข้อมูล + นักพัฒนา |
| 3. หน้าลูกค้า/LINE | ทำ Rich Menu 3×2, preview, หน้าลูกค้า และ Google Maps | ทดสอบ 6 จุดกดและเผยแพร่/rollback ด้วย LINE test account | ร้าน + นักพัฒนา + ผู้ดูแล LINE |
| 4. สมาชิก/แต้ม | อนุมัติกติกาและที่เก็บข้อมูล พัฒนา QR/ledger/แลก | ทดสอบบิลซ้ำ QR หมดอายุ ยกเลิก ยอดไม่ติดลบ สิทธิ์และ audit | ร้าน + นักพัฒนา + ผู้ดูแลฐานข้อมูล |
| 5. Integration/UAT | ทดสอบแชท publishing การจอง สต็อก และ metrics จริงตามขอบเขตที่เลือก | ร้านตรวจรับ workflow, privacy, ความถูกต้องและการแจ้งข้อผิดพลาด | ร้าน + นักพัฒนา + ผู้ดูแลช่องทาง |
| 6. Deploy/cutover | ตั้ง hosting/DNS/HTTPS/secrets/monitoring, วาง rollback | ผ่าน checklist, ผู้มีอำนาจอนุมัติ และคงระบบเดิมจนปลอดภัย | ผู้ดูแล hosting/DNS + เจ้าของระบบ |

ลำดับเป็นข้อเสนอ ไม่ใช่กำหนดวันส่งมอบ ระยะเวลาและค่าใช้จ่ายยังประเมินไม่ได้จนกว่าจะเห็น schema จริง ขอบเขต UAT และกติกาสมาชิก

## 8. แผนทดสอบและเกณฑ์รับงาน

- **Auth/สิทธิ์:** ล็อกอินจริง, ปฏิเสธผู้ไม่มีสิทธิ์ในทุก action/API, session หมดอายุ, ป้องกัน brute force และไม่เปิดเผย secret
- **ข้อมูล/transaction:** CRUD กับสำเนาฐานเดิมโดยไม่เปลี่ยน schema, ผู้ใช้พร้อมกัน, ยกเลิก/คืน, ยอดลูกค้า/สต็อกตรงกัน และทดสอบ backup/restore
- **Rich Menu:** ภาพถูกขนาด พื้นที่คลิกครบทั้ง 6 ตรงภาพ URL ถูกต้อง preview/อนุมัติ/เผยแพร่/rollback และสิทธิ์บน LINE test account
- **QR/แต้ม:** สมาชิกถูกคน QR หมดอายุ/ปลอม/ใช้ซ้ำ, บิลซ้ำ, requests พร้อมกัน, เงื่อนไขปัดเศษ/คืน/แลก/หมดอายุ และ audit
- **Integration:** webhook signature ถูก/ผิด, events ซ้ำ, ส่งไม่สำเร็จ, LINE/Facebook test account, ไม่แสดง metrics จำลองเป็นของจริง
- **Deploy:** HTTPS/cookie, DNS, process restart, monitoring, backup/restore, ทดสอบจากมือถือ, UAT และ rollback โดยไม่กระทบข้อมูลใหม่

## 9. แนวทาง Deploy และ rollback

1. เลือก hosting และแยก private staging ก่อน ตั้ง secret ผ่านช่องทางปลอดภัย ไม่เก็บใน Git หรือส่งผ่านแชท
2. หลังทำ blockers และทดสอบผ่าน ผู้ดูแล DNS ชี้ `app.laemchabanginterautotire.com` ไป hosting ที่เลือก ตั้ง HTTPS และ reverse proxy ตามแพลตฟอร์ม
3. ตรวจ production configuration, สิทธิ์, ฐานข้อมูล, logging/monitoring และ backup/restore ก่อนเปิดให้ผู้ใช้
4. เปลี่ยน webhook/ช่องทางจริงเฉพาะหลังเจ้าของอนุมัติ และคงระบบ `office.` ระหว่างเปลี่ยนผ่าน ไม่ redirect โดยอัตโนมัติ
5. บันทึก release และค่า DNS/webhook เดิม; หากมีปัญหาให้หยุดทราฟฟิกใหม่ คืนค่าช่องทางเดิมและประเมินข้อมูลใหม่ก่อน restore เพราะการ restore ทับอาจทำข้อมูลหลัง backup สูญหาย

รายละเอียดเชิงปฏิบัติและรายการ secrets: [รายงานความพร้อม Deploy](deployment-readiness.md)

## 10. การทดสอบที่มีหลักฐานและข้อจำกัด

- รายงาน deploy เดิมระบุว่า `npm ci` และ `npm run build` ผ่าน และ smoke test แบบ production โดยไม่ตั้ง secret: webhook ไม่มี signature ได้ 401, cron ได้ 503, login ได้ 200 และ dashboard ที่ไม่มี session redirect ไป login
- ผลดังกล่าวเป็นการตรวจใน workspace ไม่ใช่การรับรอง production; ยังไม่ได้ยืนยัน login จริง, MySQL, LINE API หรือระบบภายนอก
- การจัดทำรายงานฉบับนี้เป็นการตรวจเอกสารและโค้ดบางส่วน **ไม่ได้รัน integration test ใหม่ ไม่ได้แก้ฐานข้อมูล ไม่ได้ deploy และไม่ได้เพิ่มฟีเจอร์ QR หรือ Rich Menu 3×2**

## 11. ข้อมูลและการตัดสินใจที่ต้องขอจากร้าน

1. ส่ง **ลิงก์ Google Maps โดยตรง** ของร้านหรือแต่ละสาขา และเบอร์/ช่องทางติดต่อที่จะใช้ในช่องสุดท้าย
2. ยืนยันลำดับ 6 ช่อง โลโก้ สี ภาพ และข้อความ พร้อมระบุว่าต้องการให้พนักงานปรับอะไรได้บ้าง
3. ยืนยันกติกาแต้ม วิธีสมัคร/ยืนยันตัวตน และสิทธิ์ผู้อนุมัติ ตามหัวข้อ 5
4. ส่ง schema ฐานเดิมแบบลบข้อมูลส่วนบุคคล/ความลับ และระบุว่ามีสมาชิก/แต้มเดิมหรือไม่
5. ระบุผู้ดูแล hosting/DNS/LINE, test accounts, วิธีเข้าถึงที่ปลอดภัย และผู้อนุมัติ UAT/cutover **ไม่ส่ง token หรือรหัสผ่านผ่านแชท**

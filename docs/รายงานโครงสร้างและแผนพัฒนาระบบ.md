# รายงานโครงสร้างระบบและแผนพัฒนา LCB CRM + ERP

**โดเมนเป้าหมาย:** https://app.laemchabanginterautotire.com  
**วัตถุประสงค์:** สรุปสิ่งที่มีอยู่ งานที่ยังต้องทำ และข้อเสนอสำหรับระบบสมาชิกสะสมแต้มด้วย QR และ LINE Rich Menu 6 ช่อง  
**ขอบเขตการตรวจ:** ตรวจจาก source code ใน repository และงานที่อยู่ใน workspace ปัจจุบัน ไม่ได้ตรวจฐานข้อมูล MySQL, ระบบ PHP เดิม, hosting, DNS หรือบัญชี LINE จริง

> **สถานะรวม: ต้นแบบ ยังไม่พร้อมเปิดใช้งาน production** บางส่วนใช้ข้อมูลเดโมและบริการภายนอกยังไม่ได้ทดสอบจริง การตั้ง `DATABASE_URL` เพียงอย่างเดียวไม่ทำให้เชื่อมฐานข้อมูลเดิม ต้องพัฒนาและทดสอบก่อน ดูรายละเอียดความพร้อม deploy ใน [deployment-readiness.md](deployment-readiness.md)

## 1. สรุปคำตอบที่ต้องการทราบ

- **สะสมแต้มด้วยการสแกน QR:** ยังไม่ได้เพิ่มในโค้ดที่ตรวจ ไม่พบระบบสร้าง/สแกน QR, บันทึกรายการแต้ม หรือแลกแต้ม ส่วนระดับลูกค้า (tier) ที่เห็นเป็นข้อมูลเดโม ไม่ใช่ระบบแต้ม
- **LINE Rich Menu:** มีหน้าจัดการที่เชื่อม LINE API เพื่ออ่านรายการ สร้างเมนูพร้อมภาพ ตั้งเป็นเมนูหลัก และลบได้เมื่อกำหนด token แต่ยังไม่ได้ทดสอบกับบัญชี LINE จริง ตั้งได้ 1–6 ปุ่มแบบแบ่งภาพแนวตั้งเท่า ๆ กัน **ยังไม่มีผัง 3 คอลัมน์ × 2 แถว หรือ preset 6 ช่องตามที่ระบุ**
- **งานที่ร้องขอในรายงานฉบับนี้:** เสนอรายละเอียด 6 ช่อง ได้แก่ โปรโมชั่น สินค้า จองนัดหมาย สมาชิก Location → Google Maps และติดต่ออื่น ๆ โดยแก้ไขได้ รายงานนี้เป็นแผน ไม่ได้หมายความว่าได้สร้างระบบ QR หรือผัง 6 ช่องแล้ว
- **การเชื่อมฐานข้อมูลเดิม:** จะยึดฐาน MySQL และ schema เดิม ไม่เปลี่ยนชื่อตาราง/คอลัมน์หรือ migrate ข้อมูลโดยไม่ได้รับอนุมัติ ต้องตรวจ schema จริงก่อนสรุปวิธีเก็บแต้ม

## 2. สิ่งที่ทำแล้วและงานค้าง แยกตามส่วน

| ส่วน | ทำแล้วในต้นแบบ | ค้าง / ข้อจำกัด |
|---|---|---|
| โครงระบบ Next.js | App Router, หน้า login, layout และเมนูหลัก | ทดสอบ flow, performance, error handling และการรองรับใช้งานจริง |
| Cockpit | หน้าแสดง KPI, รายได้, คิว, โปรโมชัน, สต็อกและแชทจากข้อมูลเดโม | ผูกข้อมูลจริง ตรวจนิยาม KPI และความถูกต้องกับเจ้าของร้าน |
| CRM ลูกค้า | รายชื่อลูกค้า เพิ่ม/แก้ไข และหน้า 360° ที่รวมข้อมูลรถ งานและการจองเดโม | เชื่อมตารางเดิม ตรวจข้อมูลซ้ำ สิทธิ์ และการคุ้มครองข้อมูลส่วนบุคคล |
| สินค้าและบริการ | รายการ เพิ่มสินค้า ปรับสต็อก แจ้งเตือน และแสดงข้อมูลต้นแบบ | เชื่อมสต็อกและราคาเดิม ตรวจการตัดสต็อกแบบ transaction และกรณีคืน/ยกเลิก |
| โปรโมชัน | สร้างและเปลี่ยนสถานะ พร้อมส่งผ่าน publishing flow | กำหนดเงื่อนไข/วันสิ้นสุด ตรวจราคาและช่องทางส่งจริง ทดสอบการอนุมัติ |
| ศูนย์บริการ | คิวจองและ Kanban ใบงาน; demo ส่งมอบแล้วปรับยอดลูกค้า/สต็อก | เชื่อมข้อมูลจริง ตรวจสิทธิ์ การแก้ไขย้อนหลัง และความถูกต้องในหลายผู้ใช้ |
| Chat / AI | Inbox เดโมและตัวตอบแบบ intent; LINE webhook มีโค้ดรับและตอบ | ไม่ใช่ LLM; ยังต้องเชื่อมข้อมูลจริง ทดสอบ LINE, ป้องกันข้อความซ้ำและบันทึกผลการส่ง; Facebook/Web inbox จริงยังไม่ครบ |
| Publishing | มี composer และโค้ดส่ง LINE/Facebook เมื่อมี token | ไม่มี token จะจำลองผล; metrics เป็นข้อมูลสุ่ม ไม่ใช่ reach/clicks จริง; ต้องเชื่อมช่องทาง ตรวจการอนุมัติ และจัด scheduler |
| LINE Rich Menu | จัดการรายการผ่าน LINE API, สร้างพร้อมอัปโหลดภาพ, ตั้ง default, ลบ; ปุ่มแบบข้อความหรือ URL | ต้องทดสอบกับ test account; ยังไม่มี 3×2, template 6 ช่อง, preview, version/rollback และระบบแก้ไขที่ร้องขอ |
| สมาชิก / แต้ม / QR | มีข้อมูลลูกค้าและ tier เดโมเท่านั้น | ระบบแต้ม, QR, สแกน, ledger, แลกแต้มและการเชื่อม LINE **ยังไม่ได้ทำ** |
| ฐานข้อมูล | มีตัวช่วยเชื่อม MySQL (`db.ts`) แต่ CRM ยังใช้ JSON store | ตรวจ schema จริงและเชื่อม CRUD/transaction กับ MySQL เดิม; JSON ไม่เหมาะกับ production |
| Login และความปลอดภัย | มี session และการจำกัดสิทธิ์แก้ Rich Menu; งานปัจจุบันปิดบัญชีเดโมใน production และเพิ่มข้อบังคับ secret | งานความปลอดภัยใน workspace นี้ยังต้อง review/รวมเข้า branch หลัก; ยังต้องทำ auth บัญชีจริง, ตรวจ role ทุก action, rate limit และทดสอบ |
| Deploy | มีแนวทางและ checklist | ยังไม่ได้ตั้ง DNS/HTTPS หรือ deploy; production login ยังปิดอยู่จนกว่าจะสร้าง auth จริง |

## 3. โครงสร้างเป้าหมาย

```text
ลูกค้า: LINE OA / โทรศัพท์มือถือ / เว็บไซต์
          │
          ├─ Rich Menu 6 ช่อง → หน้าโปรโมชั่น / สินค้า / จอง / สมาชิก / Maps / ติดต่อ
          └─ ข้อความ LINE → webhook → inbox → พนักงานหรือระบบช่วยตอบ
                                    │
พนักงาน: app.laemchabanginterautotire.com
          ├─ Cockpit / ลูกค้า / สินค้า / โปร / ศูนย์บริการ
          ├─ สมาชิก / สแกน QR / ประวัติและแลกแต้ม (เสนอใหม่)
          ├─ จัดการ Rich Menu / publishing / รายงาน
          └─ กำหนดสิทธิ์ / audit / การอนุมัติ
                                    │
                  ชั้นบริการ + ตรวจสิทธิ์ + transaction
                                    │
          MySQL เดิมตาม schema ที่ตรวจสอบแล้ว (ไม่เปลี่ยนเอง)
```

**หลักการ:** ให้ Next.js เรียกบริการและฐานข้อมูลฝั่งเซิร์ฟเวอร์; token LINE และข้อมูลลับไม่ส่งไป browser; แยกข้อมูลทดสอบกับข้อมูลจริง; การเปลี่ยนแปลงที่มีผลต่อยอดแต้ม สต็อก และช่องทางจริงต้องตรวจสิทธิ์และมีประวัติ

## 4. รายละเอียด LINE Rich Menu 6 ช่องที่ต้องการ

### 4.1 ผังที่เสนอ — 3 คอลัมน์ × 2 แถว

| ตำแหน่ง | ช่อง | ปลายทางที่เสนอ | สิ่งที่ยังต้องยืนยัน/พัฒนา |
|---|---|---|---|
| บนซ้าย | **โปรโมชั่น** | หน้ารวมโปรโมชั่นสำหรับลูกค้า | สร้างหน้าลูกค้าจริง กรองโปรที่ใช้งานและยังไม่หมดอายุ |
| บนกลาง | **สินค้า** | หน้าแค็ตตาล็อกยาง ล้อ และบริการ | สร้างหน้าสาธารณะ ระบุว่าจะแสดงราคา/สต็อกหรือไม่ |
| บนขวา | **จองนัดหมาย** | แบบฟอร์มจองนัดหมาย | หน้าลูกค้าจริง ตรวจวันเวลา ยืนยันนัด และป้องกันสแปม |
| ล่างซ้าย | **สมาชิก** | หน้าสมาชิก / แสดงแต้ม / QR | ต้องสร้างระบบสมาชิกและระบุตัวตนที่ปลอดภัยก่อน |
| ล่างกลาง | **Location** | เปิดลิงก์ Google Maps ของร้านโดยตรง | **รอเจ้าของร้านส่งลิงก์ Google Maps ที่ถูกต้อง** และยืนยันสาขา ไม่สมมติพิกัด |
| ล่างขวา | **ติดต่ออื่น ๆ** | หน้าช่องทางติดต่อ หรือข้อความส่งเข้าห้อง LINE | รอเบอร์โทร ช่องทาง เวลาเปิด–ปิด และรูปแบบที่ต้องการ |

ตัวเลือก layout นี้เป็นข้อเสนอสำหรับผู้ใช้ยืนยัน สามารถปรับลำดับ ชื่อ ช่องทาง และภาพได้ ไม่จำเป็นต้องมีหน้าเหล่านี้อยู่แล้ว ปัจจุบันหน้า `/promotions`, `/products` และ `/service` ในแอปเป็นหน้าพนักงานที่ต้องล็อกอิน ไม่ควรนำไปเป็นลิงก์สาธารณะของลูกค้าโดยตรง

### 4.2 ข้อกำหนดการปรับแต่งที่เสนอ

1. เลือก template 6 ช่อง 3×2 หรือ layout อื่นในอนาคต พร้อมแสดงตัวอย่างตำแหน่งคลิกตรงกับภาพ
2. เปลี่ยนรูปพื้นหลัง ชื่อ/ข้อความบนภาพ ลำดับปุ่ม และปลายทางแต่ละช่องได้; เลือก action ประเภท URL หรือส่งข้อความ โดยตรวจ URL และข้อมูลก่อนบันทึก
3. ภาพและพื้นที่คลิกต้องตรงกัน: อัปโหลดภาพตามข้อกำหนด LINE และแสดง preview ก่อนเผยแพร่; ชื่อปุ่มใน metadata ไม่ได้วาดลงบนภาพให้อัตโนมัติ
4. ตั้งค่าแบบร่าง → ตรวจสอบ/อนุมัติ → เผยแพร่ → ตั้งเป็นเมนูหลัก พร้อมแสดงผู้ดำเนินการ เวลา ผลลัพธ์ และเวอร์ชันก่อนหน้า; เตรียมขั้นตอน rollback
5. ให้เฉพาะผู้ดูแลที่ได้รับสิทธิ์จัดการและเผยแพร่ ดูตัวอย่างได้โดยไม่กระทบบัญชีจริง; ใช้ LINE test account ก่อน production
6. ทดสอบจุดกดทั้งหกบนมือถือจริง ลิงก์หมดอายุ/เสีย ภาพขนาดผิด สิทธิ์ไม่เพียงพอ และกรณี LINE API ตอบ error

**ข้อจำกัดปัจจุบัน:** หน้าเดิมแบ่งพื้นที่จากซ้ายไปขวาเต็มความสูงเท่านั้น และยังไม่มีการแก้เมนูที่เผยแพร่แล้วเป็น workflow/version ตามข้างต้น ต้องพัฒนาเพิ่มและตรวจข้อกำหนด LINE API ก่อนเลือกวิธีเปลี่ยนเมนู

## 5. ข้อเสนอระบบสมาชิกและสะสมแต้มด้วย QR — ยังไม่พัฒนา

### 5.1 ขั้นตอนใช้งานที่เสนอ

1. ลูกค้าสมัคร/ยืนยันตัวตนและเชื่อมบัญชี LINE กับข้อมูลลูกค้าโดยได้รับความยินยอม; ต้องมีวิธีป้องกันการผูกผิดคนและแก้ไขเมื่อเปลี่ยนบัญชี
2. ลูกค้าเปิดช่อง **สมาชิก** ใน Rich Menu เพื่อดูข้อมูลสมาชิก ยอดแต้ม ประวัติ และ QR สมาชิก หากยังไม่เข้าสู่ระบบให้ยืนยันตัวตนก่อน
3. พนักงานที่มีสิทธิ์เปิดหน้าสแกนของแอป → ขออนุญาตกล้อง → สแกน QR → ระบบแสดงข้อมูลสมาชิกเท่าที่จำเป็นเพื่อยืนยันตัวตน; มีทางเลือกค้นหาสมาชิกเมื่อกล้องใช้ไม่ได้
4. พนักงานเลือกบิล/ใบงานที่ **ชำระและมีสิทธิ์** → ระบบคำนวณแต้มตามกฎที่อนุมัติ → แสดงตัวอย่างและยืนยัน → บันทึกเป็นรายการแต้มพร้อมผู้ทำรายการและเลขอ้างอิงบิล
5. ลูกค้าดูยอดและประวัติ; หากมีการแลก ให้แสดงรางวัล/แต้มที่ใช้และยืนยันก่อนตัดแต้ม พนักงานตรวจสิทธิ์และยอดก่อนดำเนินการ
6. การคืนสินค้า ยกเลิกบิล หรือแก้รายการ ต้องมีรายการย้อนกลับ/ปรับยอดพร้อมเหตุผลและผู้อนุมัติ โดยไม่ลบประวัติเดิม

**แนวทาง QR ที่เสนอ:** ใช้ token สุ่มอายุสั้น ตรวจลายเซ็น/สถานะฝั่งเซิร์ฟเวอร์ ไม่ใส่ชื่อ เบอร์ ยอดแต้ม หรือข้อมูลส่วนบุคคลใน QR และไม่อนุญาตให้การสแกนอย่างเดียวเพิ่มแต้ม ต้องเชื่อมบิลและยืนยันซ้ำ บันทึกการใช้ token เพื่อป้องกัน replay และแสดง QR ใหม่เมื่อหมดอายุ การกำหนดอายุจริงรออนุมัติ

### 5.2 กติกาธุรกิจที่ต้องขออนุมัติ — ยังไม่กำหนดจริง

- อัตราสะสม เช่น จำนวนเงินบาทต่อ 1 แต้ม, การปัดเศษ และคำนวณจากยอดก่อน/หลังส่วนลดหรือ VAT
- รายการที่ได้/ไม่ได้แต้ม เช่น สินค้าลดราคา ค่าบริการ ภาษี และการซื้อเงินสด/เครดิต
- จังหวะให้แต้ม: หลังชำระเงิน/ส่งมอบ, กรณีชำระบางส่วนและคืนสินค้า
- อายุแต้ม วันหมดอายุ การแจ้งเตือน และกติกาการตัดแต้มที่ใกล้หมดอายุก่อน
- ของรางวัล/ส่วนลด ขั้นต่ำในการแลก และสิทธิ์อนุมัติการแลกหรือปรับแต้มด้วยมือ
- สมาชิกซ้ำ/เปลี่ยนเบอร์/โอนแต้ม/รวมบัญชี และการแสดงผลหรือการแจ้งเตือนใน LINE

### 5.3 ข้อมูลและความปลอดภัยที่ต้องมี

- สมาชิกอ้างอิงลูกค้าเดิมและตัวระบุ LINE ที่เชื่อถือได้; QR token, บิลอ้างอิง, กฎที่ใช้, รายการเพิ่ม/ใช้/คืน/ปรับ/หมดอายุ, วันเวลา, ผู้ทำและผู้อนุมัติ
- ledger ควรตรวจสอบย้อนหลังได้ และปรับยอดแบบ atomic พร้อม transaction/locking; idempotency key ผูกกับบิลและชนิดรายการเพื่อป้องกันการกดซ้ำ/สแกนซ้ำ/requests พร้อมกัน
- กำหนดสิทธิ์แยกดูยอด เพิ่ม แต้ม แลก ปรับ และอนุมัติ; audit log และแจ้งเตือนความผิดปกติ; จำกัดการเข้าถึงกล้อง/ข้อมูลลูกค้า
- ตรวจนโยบายความเป็นส่วนตัว/ความยินยอม การเก็บรักษาข้อมูล และการลบ/ระงับข้อมูลตามข้อกำหนดที่เกี่ยวข้อง
- **ข้อจำกัด schema เดิม:** ต้องตรวจตารางและคอลัมน์ที่มีจริงก่อน ว่ารองรับ ledger, QR และ audit หรือไม่ หากไม่รองรับ ต้องเสนอทางเลือกที่ไม่แก้ schema เดิม เช่น บริการ/ที่เก็บแยกที่ได้รับอนุมัติ หรือขออนุมัติเปลี่ยนแปลงเป็นกรณีไป พร้อมแผน backup และ reconciliation; ห้ามสร้างตารางใหม่ในฐานเดิมโดยอัตโนมัติ

### 5.4 เกณฑ์ทดสอบรับงาน

- สมาชิกถูกต้องและผิดคน, QR หมดอายุ/ถูกใช้ซ้ำ/ปลอม, กล้องไม่ได้รับอนุญาต และกรณีเครือข่ายขาด
- บิลเดียวกันกดซ้ำหรือถูกสแกนพร้อมกันต้องไม่เพิ่มแต้มซ้ำ; บิลยังไม่ชำระหรือไม่มีสิทธิ์ต้องไม่เพิ่มแต้ม
- คำนวณยอด/ปัดเศษ/หมดอายุ/แลก/คืนบิลตามกติกาที่อนุมัติ; แต้มไม่ติดลบโดยไม่ได้รับอนุญาต
- สิทธิ์พนักงานไม่เพียงพอต้องถูกปฏิเสธ; รายการปรับและยกเลิกต้องมีเหตุผล ประวัติและผู้อนุมัติ
- ตรวจ transaction, reconciliation, backup/restore, ข้อมูลภาษาไทย และทดสอบกับฐานจำลองก่อนข้อมูลจริง

## 6. แผนดำเนินงานตามลำดับความสำคัญ

| ลำดับ | งาน | ผลส่งมอบ / เงื่อนไขผ่าน |
|---|---|---|
| P0 | สำรวจระบบเดิมและความปลอดภัย | schema แบบไม่เปิดเผยข้อมูลลูกค้า, mapping ระบบเดิม, auth จริง, role, แผนสำรองและ restore |
| P0 | เชื่อม MySQL เดิม | CRUD/transaction กับตารางเดิมผ่าน staging; ไม่เปลี่ยน schema; ทดสอบข้อมูลและ concurrency |
| P1 | Rich Menu 6 ช่องปรับแต่งได้ | template 3×2, preview, ตรวจ URL, สิทธิ์และ workflow เผยแพร่/rollback; ผ่าน LINE test account |
| P1 | หน้าลูกค้า | โปรโมชั่น สินค้า จอง สมาชิก และติดต่อที่เหมาะกับมือถือและมีสิทธิ์/ความเป็นส่วนตัวถูกต้อง |
| P1 | สมาชิกและ QR | ยืนยันกติกาและ storage → พัฒนา ledger/QR/สแกน → ทดสอบรายการซ้ำ แลก ยกเลิก และ audit |
| P2 | LINE chat / publishing / analytics | เชื่อมจริง แยกจากเดโม ป้องกันส่งซ้ำ เก็บผลส่ง และ metrics จริงตามสิทธิ์ API |

ลำดับ P1 สามารถออกแบบคู่ขนานได้ แต่ยังไม่ควรเปิดช่องสมาชิกหรือให้แต้มจริงจนผ่าน P0 และกติกาการเก็บข้อมูลได้รับอนุมัติ

## 7. ข้อมูลที่ต้องขอจากเจ้าของร้าน

1. ลิงก์ **Google Maps โดยตรงของร้าน/แต่ละสาขา** และข้อมูลติดต่อที่จะใช้ในช่องสุดท้าย
2. ยืนยันลำดับ 6 ช่องตามตารางหรือแจ้งลำดับใหม่; โลโก้ สี ภาพ และข้อความบน Rich Menu
3. กติกาสะสมและแลกแต้มตามหัวข้อ 5.2, สิทธิ์ของพนักงาน และวิธียืนยันตัวตนสมาชิก
4. schema ฐานข้อมูลเดิมแบบลบข้อมูลส่วนบุคคล/ความลับ และข้อมูลว่ามีระบบสมาชิก/แต้มเดิมหรือไม่
5. ผู้ดูแล DNS/hosting และบัญชี LINE test; ส่ง token/รหัสผ่านผ่านระบบจัดการความลับที่ปลอดภัยเท่านั้น ไม่ส่งในแชท

## 8. สถานะการเปลี่ยนแปลง

รายงานนี้อธิบายทั้งสิ่งที่อยู่ใน `main` และมาตรการความปลอดภัยที่ทำใน workspace/branch ปัจจุบันแต่ยังไม่ได้รวมเข้า `main` ณ เวลาจัดทำ ต้อง review และ merge ตามขั้นตอนก่อน deploy รายงานนี้ไม่ได้เปลี่ยนฐานข้อมูล ไม่ได้เปิดใช้งาน QR หรือ Rich Menu แบบใหม่ และไม่ได้ตั้ง DNS หรือ deploy ระบบ
